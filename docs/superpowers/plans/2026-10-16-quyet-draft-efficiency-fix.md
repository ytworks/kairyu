# 計画：書き手がそのまま答え、Quyet が「コールを減らせるか」を判定し、減らせるときだけ 1 回直す（DeepSeek+Quyet・GLM+Quyet、VCO-D27）

状態: 承認 2026-10-16（VCO-D27）、同日改訂（ゲートは動作の保証、精度は DeepSWE で測る）。PR #654（VCO-D26）を置き換える。ブランチ: `claude/quyet-draft-efficiency-fix`。

## 0. 目的と範囲

- **目的（オーナーの言葉）:** マルチターンの課題を解き切るまでの API コール数を減らす。その結果、入力トークンが減り、時間も短くなる。正解率は落とさない。
- **対象:** decision model（Quyet）のオーケストレーションだけ。`examples/deepseek-v4.1-quyet-8gpu`、`examples/glm-5.3-flash-quyet-8gpu` の L2（ルート判定と DSL の構成）をすべて作り直す。
- **変えないもの:** `kairyu/`（既存の DSL で書けるため、フレームワークは変えない）、L1、GPU の割り当て（DeepSeek/GLM は GPU 0–5、Quyet は GPU 6・7 の 2 台）。Qwen が判定するほかの example。
- **置き換えるもの:** 今のルート判定（Quyet が TOOL/THINK を選ぶ `profile_judge`）、候補方式（候補 10〜16、Quyet の 6 問判定、形式チェック）、think ルート。PR #654（VCO-D26）はこの計画で置き換わるので閉じる。
- **ブランチ:** main から新しく `claude/quyet-draft-efficiency-fix`（指定の `claude/winnow-verified-three-wave` はマージ済み PR #641 の履歴を持つので使わない）。

## 1. 新しい流れ（どの要求も同じ 1 本。ルート判定はなくなる）

```
answer    書き手（DeepSeek / GLM）。呼び出し元の effort で、呼び出し元の会話をそのまま受け取り、
          プロンプトを足さずに答える（今の think ルートと同じ答え方）
decision  Quyet（GPU 7、strict）。答えと、ツールの一覧と、会話を読み、5 つの問い（2 章）に 1 回で答える
          → すべて 0.5 以上なら、答えをそのまま返す
          → 1 つでも 0.5 未満なら、書き手に「入力の会話 + 答え + Quyet の結果（満たさない問いと確率）」を渡して 1 回直させ、直した答えを返す
```

- DSL：`answer`（publisher、`native_conversation: true`、`prompt` なし、`refine_prompt` あり）＋ `decision`（verifier、checklist 5 問、`max_refinements: 1`、`on_unavailable: publish_unverified`）。`profile_judge`・`profiles`・think ルートは消す。
- 直した答えも DSL の作りで Quyet がもう一度読む（返す答えは変わらない。直しで問いが満たされたかの記録になる）。
- Quyet が読めないとき（6,000 トークンを超える、止まっている）は、答えをそのまま返す。
- ツールのない会話も同じ流れ。5 問はすべて満たされるので、答えはそのまま返る。
- GPU 6 の Quyet（quyet-route）は判定に使わなくなるが、L1 は変えないので配置したままにする（使わない部品を残した前例：サンドボックス実行器）。

## 2. 判定する項目（必要十分の 5 問）

**考え方:** 1 つの返答が後の API コールを増やすのは、次の 5 つの場合だけ。どれにも当たらなければ、直しても API コールは減らない（だから直さない）。逆に、どれか 1 つでも当たれば、直すことでコールを減らせる。

| ID | 問い（満たすと「はい」） | 当たらないとき、後で増えるコール | 直し方 |
|---|---|---|---|
| E1 まとめ残し | いま必要で、この返答のほかのコールの結果を待たずに出せるコールを、後の返答に残していないか | 残したコール 1 つにつき返答 1 回 | そのコールを足す |
| E2 動かない返答 | 作業が終わっていないのにツールコールがない、言った操作をコールしていない、コールを本文に書いている、のどれでもないか | 何も進まない返答 1 回（形式エラーの往復を含む） | コールとして出す |
| E3 無効なコール | どのコールも宣言されたツールを、正しい引数で呼んでいるか | エラーが返り、やり直しの返答 1 回 | 正しいツール・引数にする |
| E4 繰り返し | 会話に結果がすでに出ていて、その後何も変わっていない操作を、もう一度していないか | むだな返答 1 回 | そのコールを外し、次に必要なコールにする |
| E5 互いに依存 | 1 つの返答のコールどうしが、互いの結果を必要としていないか（会話が 1 返答 1 コールを求めていないか） | 前提が崩れたコールの失敗と、やり直しの返答 | 結果を待つコールを外し、次の返答に回す |

- **入れないもの（理由）:** 安全（壊す操作）と早すぎる終了は、コール数ではなく正しさの問題で、答えは単体と同じ書き手がそのまま書くので単体と同じ扱いにする。直すときの指示（refine_prompt）では、足すコールが安全であること、終了のコールを足さないこと・1 つだけで成功を確かめた後に出すことを守らせる。出力の大きさは、実行前の Quyet には見えないので問わない。
- 問いの文と基準の書き方は、前回までに Quyet が読めた形（D24 の R1・S2・F1〜F4）を土台にする。しきい値は 0.5（VCO-D16）。
- Quyet が読む state：答え（本文の後にコールを `<tool_call>` で並べたもの）、ツールの一覧、会話（1 メッセージ 2,000 文字、全体 6,000 文字。依頼と最新のメッセージを残す）。strict で 1 回読む。
- 直しの指示：判定は間違うことがあるので会話で確かめる、満たさない問いが求めることだけ変え、ほかのコールと本文はそのまま残す、すべてツールの仕組みで呼ぶ、会話が求める形式で書く。

## 3. 判定の精度について（改訂 2026-10-16）

- ゲートは動作を保証し、判定の精度は保証しない。精度と効果（API コール数、入力、時間、正解）は DeepSWE で測る（オーナー 2026-10-16）。実装の前の精度の試験はやめた。
- 参考の記録：単体 DeepSeek max の実返答 120 件では、Quyet の E1 の確率は「まとめ残しあり」と「むだなし」でほぼ同じ分布だった（4 通りの文言と会話の量で、精度 49〜57 %）。E2〜E4 は記録に 0 件。直しが当たるかの精度は DeepSWE の結果で判断する。
- 問いの文は 2 章の最初の文（D24 の R1・S2・F1〜F4 が土台）を使う。この文では直しに回る返答は 5〜10 % ほどだった。

## 5. GPU ゲート（動作の保証。GATES の全項目から作り直す）

| # | ゲート | 保証する動作（合格の基準） | 時間 |
|---|---|---|---|
| 1 | l1 | 変更なし | 10 分 |
| 2 | decision（旧 routing・verified-tool-route） | 実ターン 12 件 × 通常／ストリーム：どの要求も書き手の答えのあと Quyet が 5 問を 1 回読む。5 問すべて 0.5 以上なら書き手の答えがそのまま返り、直しのコールはない。どれか 0.5 未満なら直しのコールがちょうど 1 回あり、その入力に会話・答え・満たさない問いと確率が入り、直した答えが返る。どちらも構造化されたコールで、max で 1 件も 900 秒を超えない。トレースと `kairyu_verification` に判定が残る | 60 分 |
| 3 | text（旧 think-route） | ツールなしの会話：答えが返り、エラーにならない | 15 分 |
| 4 | effort | 答えと直しが呼び出し元の effort に従う | 60 分 |
| 5 | fallback | Quyet を止めると、答えがそのまま返る（エラーにならない） | 30 分 |
| 6 | serving | 実ターン 24 件を c1/c4/c8/c16。全件応答し、すべて構造化されたコール、900 秒以内。2 の規則がすべての要求で守られる。直しの割合と、答え・判定・直しごとの時間 p50/p95/最大を記録（精度の基準は置かない） | 2 時間 |
| 7 | serving-mixed（旧 serving-routed） | ツールあり・なしを混ぜて全件応答 | 1 時間 |
| 8 | browser | 変更なし | 5 分 |

- 直しの分岐が実ターンで 1 回も起きなかったときも、直しの動作は CPU テスト（会話・答え・判定結果が直しの入力に入ること）で保証し、GPU では起きた回数を報告する。
- 不合格が出たらその場で止め、分かっているリスクをすべて（観測した割合つきで）まとめて直し、該当するターンだけで確かめてから、全体を 1 回だけ回し直す。

## 6. DeepSWE（ゲート合格の後、DeepSeek → GLM の順）

- 条件：kairyu-bench main、113 問、8 並列、1 回ずつ、`RETRIES=3`、`API_TIMEOUT_SECONDS=3600`、`REASONING_EFFORT=max`、専用の DinD と relay の記録。
- run 名：`deepswe-deepseek-v4.1-quyet-d27-max-8w-<日付>-r1`、`deepswe-glm-5.3-flash-quyet-d27-max-8w-<日付>-r1`。
- 比べる相手：単体 DeepSeek 6GPU max（85/113、1 問 194.5 API コール、入力 3,860 万、51.9 分）、単体 GLM 6GPU max（72/113、136.2、1,540 万、32.9 分）。参考に候補方式 DeepSeek+Quyet 8GPU high（67/113）。
- **成功の基準（同じ 113 問で単体 max と比べる）:** L3 の API コール数と L3 入力が単体より少ない、1 問の時間が単体以下、正解が単体以上（1 回ずつなので ±数問は誤差として報告）、900 秒の切断 0、3 時間の時間切れ 0。
- 止める条件（これだけ）：最初の 15 分で `RepeatedFormatError`、ツールコールのない返答が 10 % 超、HTTP エラーが続く、`reasoning_effort: max` のない要求。それ以外は最後まで回す。再実行は通信障害などの事故だけ。
- 進捗の報告は毎回同じ詳しさ（正解、API コール数 L3/L1、ツールコール数、トークン、tok/s、直しの割合）。
