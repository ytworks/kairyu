# 計画 v2：ルート判定を汎用のロールの組み合わせで書き直す（DeepSeek+Quyet・GLM+Quyet）

状態: 承認 2026-10-16（v1 を置き換え、VCO-D26）。ブランチ: `claude/quyet-parallel-moment-route`。v1 の条件・ファクト・DeepSWE・wiki の内容は、この版の該当章に引き継ぐ。

## 0. 目的

- ルート判定を直す。書き手が会話を要約し（effort low 固定）、Quyet がその要約を読んで葉を選び、選ばれた葉で「マルチターンのルート（候補方式）」か「単体のルート」かが決まるようにする。
- これを、専用の部品（`profile_judge`）ではなく、プロンプトを指定したふつうのロールの組み合わせで書く。フレームワークに足すのは、その組み合わせに足りない汎用の仕組みだけにする。
- 対象：`deepseek-v4.1-quyet-8gpu`、`glm-5.3-flash-quyet-8gpu` のルート判定。マルチターンのルート（候補方式）の DSL と単体のルートの中身は変えない。

## 1. 今の作りと、汎用でないところ

| 今の作り | 何が決め打ちか |
|---|---|
| `profile_judge`（2026-08-17 に issue #509 で追加、10-01 に System One 版） | 位置（どのロールより先に 1 回）、入力（切り詰めた会話と印だけ）、出力（プロファイル名）。ほかのロールの出力をつなげない |
| choice の数だけ別のプロファイルが要る決まり | 6 つの葉のうち 5 つが同じ単体のルートなのに、名前だけ違うプロファイルを 5 つ置く必要がある |
| checklist の問いは noul（はい／いいえ）だけ | System One が持つ choice（選択式）を、ロールからは使えない |
| `native_conversation` は publisher だけ | 要約のように、会話を読んで返答以外を書くロールに会話をそのまま渡せない |

## 2. フレームワークに足す汎用の仕組み（`kairyu/`、すべてどの example でも使える）

| 足すもの | 中身 | 置き換えるもの |
|---|---|---|
| **選ぶ前のロール（`select`）** | DSL の上位に `select:` を置く。中身はふつうのロールの並び（ワーカー、プロンプト、`depends_on`、推論の強さ、サンプリング、checklist）。プロファイルを選ぶ前に実行し、最後の判定ロールの choice の答えで、動かすプロファイルを決める（`labels: {ラベル: プロファイル}`、複数のラベルが同じプロファイルを指してよい）。答えられなければ `fallback` のプロファイル | `profile_judge` が持っていた「最初に 1 回だけ、会話だけを読む」決め打ち |
| **choice の問い** | checklist の問いに `type: choice`（選択肢とその基準）を足す。答えは各選択肢の確率。noul はこれまでどおり | なし（今は noul だけ） |
| **会話をそのまま渡す指定を、どのロールにも** | `native_conversation` を publisher 以外の生成ロールにも許す（会話の後にプロンプトを 1 つ足す形は今と同じ） | publisher だけの制限 |

- 実行の場所は、今 `profile_judge` が走っているところ（`app.py` から呼ぶ `judge_role_profile`、プロファイルの見積もりより前）と同じにする。だから受け入れ量の見積もりや計測の流れは変わらない。
- 選ぶ前のロールのコール、トークン、時間は、ほかのロールと同じように `kairyu_trace_v2` と使用量に記録する。どの選択肢の確率がいくつだったかも、トレースに残す。
- `profile_judge` は今回は消さない。Qwen が判定する 2 つの example が使っているため。消すのは、それらを `select` で書き直す別の作業にする（10 章）。

## 3. 2 つの example のルート判定（`select` で書く）

```
select:
  roles:
    - route_note   書き手（DeepSeek / GLM）、reasoning_effort: low（固定）、会話をそのまま受け取り、
                   最後に「判定のための事実のメモ」を書く指示を 1 つ足す。ツールは呼ばない
    - route        Quyet（GPU 6）、choice の問い 1 つ。state は route_note の出力とツールの有無
  labels: {MANY: primary, TEXT: think, FAILED: think, AFTER_ACT: think, ONE: think, FEW: think}
  fallback: think
```

- **メモに書かせる事実（判断はさせない）:** ツールが要るか／直前の結果が失敗したか／直前の返答が何をしたか（読む・変更・実行・終了）／ここまでに読んだもの・変えたもの／依頼に必要でまだ読んでいない・実行していないもので、互いの結果を待たずにいま出せるものの数と名前。
- **Quyet の問い（v1 の 6 つの葉）:** 上から順に、TEXT（ツールが要らない）→ FAILED（直前の結果が失敗）→ AFTER_ACT（直前が変更・実行・終了）→ 残りは、いま出せる読む・実行のコールの数で ONE（1 個以下）／FEW（2〜7 個）／MANY（8 個以上）。MANY だけがマルチターンのルートに入る。
- 単体のルート（`think`）は 1 つで済む。名前だけ違うプロファイルは置かない。
- 予算の `max_steps` などは、選ぶ前のロールの分（要約 1、判定 1）だけ増やす。

## 4. 実装の前の試験（フレームワークを変えず、作業用のスクリプトで。約 1 時間）

- 試験の材料：v1 で作った実ターン 600 件（単体 DeepSeek max と GLM max の記録、葉ごとに 60 件）と、合成のルート判定セット 136 件。
- やり方：書き手を effort low で直接呼んで 3 章のメモを書かせ、そのメモを state にして、quyet-route に 6 つの葉の choice の問いを送る。DeepSeek の試験は DeepSeek の記録で、GLM の試験は GLM のスタックで行う。
- 合格の基準（v1 と同じ）：
  - マルチに送ったターンのうち本当に MANY だった割合（精度）が 70 % 以上
  - MANY を 40 % 以上拾う
  - FAILED・AFTER_ACT をマルチに送るのが 2 % 以下
  - 合成セットの TEXT は main の基準（ツールの見逃し 10 % 未満、単体の精度 90 % 以上）
- あわせて測るもの：メモ 1 回の時間（p50 / p95）、入力と出力のトークン数。前回のキャッシュが効く再送の時間。
- 届かなければ：メモの指示と問いの文言を 1 回だけ直す。それでも届かなければ止めて、結果を持ってくる。

## 付録：計画 v1（承認 2026-10-16。ファクトと条件の根拠、ゲート、DeepSWE、wiki の詳細）


### v1 0. 目的と前提

- **目的（オーナーの言葉どおり）:** DeepSWE のようなマルチターンの課題で、ツールコールを 1 回の API コールにできるだけまとめ、API コール数と入力トークン数を減らす。ただし、問題を安全に解き切り、正解率を落とさない。L3 の 1 コールの時間は、max でも長くなりすぎないようにする。
- **手段:** ルート判定だけを変える。適切なときだけ verified tool（以下「マルチターンのルート」＝ main の候補方式）に入り、それ以外は書き手が 1 回で答える（以下「単体のルート」＝今の think ルート）。
- **変えないもの:** マルチターンのルートの DSL（候補 10〜16、Quyet の 6 問判定、answer、形式チェック F1〜F7、予算）、単体のルートの中身、L1 と GPU の割り当て、`kairyu/`。
- **対象:** `examples/deepseek-v4.1-quyet-8gpu`、`examples/glm-5.3-flash-quyet-8gpu`。
- **「検証項目の最適化」の解釈:** example の GPU ゲート（データ・合格基準・時間）を新しい条件に合わせて作り直すこと。マルチターンのルートの中の判定項目は変えない。
- ブランチ: main から新しい `claude/quyet-parallel-moment-route`（指定の `claude/winnow-verified-three-wave` はマージ済み PR の履歴を持つので使わない）。

### v1 1. 言葉の定義（源流＝エージェントが送る会話。DeepSWE では mini-swe-agent のプロンプト）

- **返答:** アシスタントのメッセージ 1 つ（＝L3 の API コール 1 回）。説明の文と、ツールコール 0 個以上。
- **ツールの結果:** ツールコールへの応答のメッセージ。**失敗**＝結果がエラーを返している（DeepSWE では `returncode` が 0 でない）。
- **手の種類（ツールコールの中身で決める、一般的な意味）:**
  - 読む：内容を表示する・探す・一覧する。何も変えず、作業のプログラムも動かさない。
  - 実行：プログラム（テスト、ビルド、スクリプト）を動かして出力を見る。ファイルは書かない。
  - 変更：ファイルやデータを作る・書き換える・移す・消す、入れる（install）。
  - 履歴の操作：ブランチの作成・切り替え、ステージ、コミット（変更とは分けて数える。前回の誤りの原因）。
  - 終了：会話が定める終了のコール（DeepSWE では `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`）。
- **並列にできるコール:** いま出せて、同じ返答のほかのコールの結果を待たずに引数と安全が決まるコール。
- **Quyet に見える範囲:** タスクの最初のメッセージの先頭 4,000 文字、直前のツールの結果、その手前の返答 3 つほど（今の `bounded_conversation` 12,000 文字）。

### v1 2. ファクト（記録から。数字は既存の wiki・記録の値か、今回の読み取り専用の集計）

対象 run：単体 DeepSeek 6GPU max（85/113、1 問 194.5 コール、入力 3,860 万、51.9 分）、単体 GLM 6GPU max（72/113、136.2 コール、1,540 万、32.9 分）、候補方式 DeepSeek+Quyet 8GPU high（全ターンがマルチターン、67/113）。

#### 2.1 返答の直前に見える状態ごとの「次の手」と「まとめた数」

| 直前の状態 | 単体 max：1 問あたり | 単体 max：次の手 | 単体 max：その後に続く「読む」コールの数（平均・10 個以上の割合） | 候補方式：1 返答のコール数（4 個以上の割合） | 候補方式：1 返答の時間 p50 |
|---|---:|---|---|---|---:|
| まだ何もしていない（最初の返答） | 1.0 | 読む 98 % | 11.6・56 %（GLM 15.6・73 %） | 81 % | （r1 max で約 170〜200 秒） |
| 直前が読む（成功） | 76.1 | 読む 62 %、変更 19 %、実行 15 % | 3.0・9 % | 66 % | 242 秒 |
| 直前が実行（成功） | 46.5 | 実行 44 %、読む 28 %、変更 25 % | 0.75・1 % | 35 % | 224 秒 |
| 直前が変更 | 59.0 | 変更 53 %、実行 24 %、読む 21 % | 0.39・0 % | 29 % | 239 秒 |
| 直前の結果が失敗 | 8.1 | 実行 37 %、読む 33 %、変更 22 % | 1.2・3 % | 32 % | 212 秒 |

- 単体はほぼまとめない（DeepSeek 1.04、GLM 1.07 コール/返答）。まとめるのはマルチターンのルートだけ。
- まとめる余地（読むコールが続く）は「最初の返答」と「直前が読む」に集中し、変更・実行・失敗の後にはほとんどない。

#### 2.2 マルチターンのルートの効率は「まとめた数」で決まる（候補方式 high、2,672 返答）

| 1 返答のコール数 | ツールコール 1 個あたりの時間 |
|---|---:|
| 1 | 212 秒 |
| 2〜3 | 118 秒 |
| 4〜6 | 58 秒 |
| 7〜9 | 27 秒 |
| 10 以上 | 14.6 秒（単体の読む 1 コール 8〜15 秒とほぼ同じ） |

- マルチターンの 1 返答は 150〜300 秒（max の r1 で p50 200 秒・最大 353 秒、ゲートでは暴走 1 件 2,353 秒）。数が少ない返答ほど損をする。
- 正解への影響（片方だけ正解の 21 問）：テストを重ねて直す場面はマルチターンの 0 勝 6 敗。並列で多く出したことが勝因になった例は 0。

#### 2.3 Quyet が読めるもの・読めないもの（前回の 651 ターン試験）

- 読める：会話にすでに変更があるか（95 % / 誤り 0.3 %）、ツールが要るか（main で検証済み）。
- 読めない：次の返答が変更を含むか（要約を足しても不可、誤りが 10.4 % に増えた）。
- → 条件は「見えている状態」で決め、次の手の予測は「まとめられる数」の 1 問だけに絞る。その 1 問が読めるかは、実装前に試験で確かめる（4 章）。

#### 2.4 見込み（単体 max の記録で、読むコールが N 個以上続く区間をマルチターンが 5 個ずつまとめたと仮定。マルチターン 1 返答 250 秒）

| 入る区間 | L3 コール数 | L3 入力 | 書き手の入力 | Quyet の入力 | 1 問の時間 |
|---|---:|---:|---:|---:|---:|
| 読むが 4 個以上続く | −15.0 % | −7.6 % | −163 万 | +226 万 | +72 % |
| 6 個以上 | −11.5 % | −4.4 % | −89 万 | +181 万 | +59 % |
| **8 個以上** | **−9.0 %** | **−3.1 %** | −69 万 | +133 万 | **+43 %** |
| 10 個以上 | −7.4 % | −2.2 % | −48 万 | +110 万 | +35 % |

（GLM も同じ傾向。見込みは代理の計算で、本当の値は DeepSWE で測る。）

**ファクトから言えること:** マルチターンのルートは、どの場面でも時間では単体に勝たない。減らせるのは API コール数と L3 入力で、その代わりに時間が増える。増え方は「入る回数」と「1 回でまとめる数」で決まるので、まとめる数が多い場面だけに入るほど効率がよい。

### v1 3. ルートの条件（多段判断、MECE）

上から順に判断し、どのターンも必ず 1 つの葉に入る。

| 段 | 問い | 当てはまれば | 葉 | 理由（ファクト） |
|---|---|---|---|---|
| 1 | 次の返答にツールコールが要らない | 単体 | `TEXT` | まとめるものがない（main で検証済みの問い） |
| 2 | 直前のツールの結果が失敗 | 単体 | `FAILED` | まとめる余地 1.2、マルチは 1 返答 3 コール・212 秒、直す場面は 0 勝 6 敗 |
| 3 | 直前の返答が変更・履歴の操作・実行・終了を含む | 単体 | `AFTER_ACT` | 次も変更か実行が多く（7〜8 割）、まとめる余地 0.4〜0.75 |
| 4 | （まだ何もしていないか、直前が読むだけで成功）いま互いの結果を待たずに出せる「読む・実行」のコールは何個か：1 個 / 2〜7 個 / **8 個以上** | 8 個以上ならマルチ、それ以外は単体 | `MANY`（＝ここぞ）/ `ONE` / `FEW` | 8 個以上まとめるとコール 1 個あたりの時間が単体に近づく（2.2）。最初の返答の 56〜73 % がこれに当たる |

- **おすすめの境目は 8 個**（見込み：コール −9 %、L3 入力 −3 %、時間 +43 %）。時間を優先するなら 10 個（−7.4 %、+35 %）。ここはオーナーに決めていただく（下の「決めること」1）。
- **Quyet への聞き方:** 1 回の読み取りで、6 つの葉から 1 つを選ぶ choice の問い（問いの文に段の順番を書く）。各葉の criteria は上の表のとおり互いに重ならない書き方にする。`prefer` は使わず、最も確率の高い葉で決める（4 章の試験で、`MANY` の確率の下限が必要なら付ける）。
- **DSL の制約:** 選択肢ごとに別のプロファイルが要る（`kairyu/dsl/spec.py`）。単体側の 5 つの葉には、中身が今の think ルートと同じプロファイルを名前だけ分けて置く（前回の試験で使った形）。どの葉に入ったかがトレースに残り、wiki の内訳にも使える。
- `max_message_chars` 4,000、`max_conversation_chars` 12,000、`timeout_seconds` 60、フォールバックは単体のまま。

### v1 4. 実装の前の試験：Quyet が条件を読めるか（GPU 約 30 分、リポジトリは変えない）

- **材料:** 単体 DeepSeek max と GLM max の記録から、葉ごとに実ターンを選ぶ（各葉 60 件、`MANY` は「その後に読む・実行のコールが 8 個以上続いた」ターン、`ONE/FEW` は 0〜7 個のターン）。正解の葉は記録から 1 章の定義で付ける。
- **やり方:** 前回の `tree_eval.py` と同じく、サービス中の quyet-route に実際の判定の形で送る。
- **合格の基準:**
  - マルチに送ったターンのうち、本当に `MANY` だった割合（精度）が 70 % 以上
  - `MANY` のターンを 40 % 以上拾う（拾えなかった分は単体に行くだけで、正解率は下がらない）
  - `FAILED`・`AFTER_ACT` のターンをマルチに送るのが 2 % 以下
  - `TEXT` は main の routing ゲートの基準のまま
- **届かなければ:** 文言を 1 回だけ直して試す。それでも届かなければ止めて、結果と次の案（例：段 4 を「最初の返答だけ」に絞る）を持ってくる。フレームワークの変更（要約の段など）は提案しない。
