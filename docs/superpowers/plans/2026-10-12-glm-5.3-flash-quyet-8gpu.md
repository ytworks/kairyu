# GLM-5.3-Flash + Quyet: GLM を書き手とする verified tool route（2026-10-12）

状態: **ドラフト、オーナー承認待ち**（VCO-D23 として提案）。2026-10-12 に PR #647
に合わせて改訂（GLM プールを `upstream_chat_models` に変更、#647 に依存）。
ブランチ: `claude/glm-5.3-flash-quyet-8gpu`。GPU 検証は計画を書いたマシンでは
実行できないため、ドラフト PR に残タスクとして記載する。

## 背景

`examples/deepseek-v4.1-quyet-8gpu`（VCO-D21/D22、PR #645）は、GPU 0〜5 の
DeepSeek-V4.1 DP6/EP6 を書き手とし、Quyet-1.0-Large 2 台（GPU 6: ルート判定、
GPU 7: 候補の評価と形式チェック）を組み合わせて、公開モデル
`kairyu-verified-tool` 1 つとして提供している。`examples/glm-5.3-flash-6gpu`
（PR #644）は、同じ 6 GPU 上で公式 FP8 の GLM-5.3-Flash を TP2 × DP3 / EP6、
MTP 3、標準の vLLM v0.31.0 で動かし、9 つのゲートすべてを通っている。

提案する範囲:

1. 新しい example `examples/glm-5.3-flash-quyet-8gpu` を作る。DeepSeek 版は
   比較の基準としてそのまま残す。
2. L1: GPU 0〜5 は `glm-5.3-flash-6gpu` で選んだ GLM-5.3-Flash の構成のまま
   DeepSeek と置き換える。GPU 6、7 の Quyet 2 台は `deepseek-v4.1-quyet-8gpu`
   と同じ。
3. L2: Quyet example の `verified-tool.yaml` をコピーし、書き手の役割
   （candidates、answer とその修正、think ルート）をすべて GLM にする。ルート
   判定、Quyet の質問、しきい値、状態、予算は変えない。GLM のために変える必要が
   あるものだけを変える（下の表）。
4. L3: 公開モデル `kairyu-verified-tool` と Open WebUI。
5. `kairyu/` は変更しない（下で確認）。スクリプト、テスト、データセット、設定は
   すべて新しい example 自身のものとし、元の 2 つの example は参照するだけにする。

## フレームワーク変更が不要であることの確認

- 推論の強さ: `reasoning_effort: inherit` の役割は `reasoning_effort` を送る
  （Kairyu で low / high / max に正規化され、GLM 公式テンプレートはその値を
  そのまま受け付ける。`kairyu/engine/openai_backend.py`
  `_validated_request_payload`）。conductor が `enable_thinking` を付けるのは、
  そのワーカーのプールがその kwarg を許可している場合だけ
  （`kairyu/orchestration/conductor.py` `_worker_chat_template_kwargs`）。GLM
  プールは何も許可しないので、GLM に `chat_template_kwargs` は届かない。GLM の
  役割はすべて推論の強さを宣言する。PR #644 で見つかった制約（古いチャット経路が
  テキストの `chat_template_kwargs` を拒否する）は当てはまらない。公開モデルは
  オーケストレーターで、書き手の役割は kwargs を送らないため。
- ルート判定の `enable_thinking: false` も、それを許可するワーカーにしか送られない。
  判定役は System One 経由の Quyet。
- チェックリスト検証、`foreach`、`max_questions_per_call`、`refine_prompt`、
  strict な System One が拒否したときの `publish_unverified`、会話をそのまま渡す
  仕組み（native conversation）、`<tool_call>` 表記は、どれもモデルに依存しない
  （m1 D8、m1 D9）。

GLM に送られるリクエストの中身（推論の強さがあること、`chat_template_kwargs` が
ないこと）を CPU テストで確かめ、フレームワーク側の後退が GPU ではなくここで
見つかるようにする。

## PR #647 後の GLM プール（2026-10-12 改訂）

PR #647（オープン中。計画 `docs/superpowers/plans/2026-10-12-upstream-chat-messages.md`、
m9 D2 の upstream-chat 修正）で、GLM プールの古いチャット経路がエージェントの会話を
1 つのユーザーメッセージにまとめてしまい、その結果 GLM が 2 ターン目以降でツールを
一度も呼ばなくなることが分かった（`glm-5.3-flash-6gpu` での DeepSWE: 終わった
23 タスクすべてが `RepeatedFormatError`。同じリクエストを vLLM に直接送ると呼び出しが
返った）。#647 は `upstream_chat_models` を追加し、`glm-5.3-flash-6gpu` をそちらに
移している。この example への影響:

1. **チャット設定。** 起動時には、提供するすべてのプールにチャット設定が必要
   （`kairyu/deploy/builder.py` のチャット設定の解決）。GLM プールは、#647 後の
   `glm-5.3-flash-6gpu` と同じく `legacy_chat_models` ではなく
   `upstream_chat_models` に入れる。Quyet プールは古い経路のまま（System One 専用で
   チャットには使わない）。これにより、GLM のレプリカが静的な vLLM `openai`
   バックエンドでなければ起動に失敗する。プールは内部用
   （`public_models: [kairyu-verified-tool]`）なので公開経路は変わらないが、Kairyu
   経由の L1 確認や将来の直接利用も直った経路を通り、プール設定も GLM 単体の example
   と同じになる。**依存: #647 が先にマージされること。** その後この PR に main を
   取り込んでから example をコミットする。
2. **L2 の役割はまとめ送りの影響を受けない。** オーケストレーターの役割は自分で
   リクエストを組み立て、プールのチャット設定を使わない。`answer`、その修正、
   `glm_think_answer` は会話をそのまま渡す publisher 役（m1 D8 の 2026-10-09 修正）
   で、呼び出し元のメッセージはもともと `conversation_prefix` 経由でターンのまま
   vLLM に届いている（#647 と同じ仕組み）。`candidates` は publisher ではなく
   （会話をそのまま渡す設定は publisher 専用）、会話を JSON 文字列としてプロンプト
   内で読み、ツール呼び出しではなく JSON を返すので、ターンのまま渡す必要はない。
   ただし #647 で、GLM はまとめられた会話の読み取りが DeepSeek より弱いと分かった
   ので、ゲート前の確認で実際のエージェントのターンに対して候補が正しく出るかを測る。
3. **推論の強さ。** オーナーは #647 の DeepSWE 実行を max（GLM 公式の既定）で
   回すと決めている。これにより、オーナーから別の指示がない限り、決めていただき
   たいことの 1 は `max` の方向で決まる。
4. **証拠の再利用。** #647 の GLM の GPU 作業（会話をそのまま渡した状態での
   `glm-5.3-flash-6gpu` の 9 ゲート、`reasoning_effort: max` を含む Kairyu から
   vLLM への送信内容の取得、DeepSWE 実行
   `deepswe-glm-5.3-flash-6gpu-max-8w-<date>-r1`）を、この example の GLM 単体の
   基準とする。この example の GPU 検証を始める時点でそれが終わっていなければ、
   ここの L1 は会話をそのまま渡す経路で未検証なので、最初のゲートで同じ取得を行う。
5. **既知の制約（該当しない）。** #647 では、会話をそのまま渡すチャットについて
   KV を意識した配置が空のプロンプトを読む。GLM プールはレプリカ 1 台なので配置は
   変わらない。

## 書き手を GLM にすることで変わる点

| 項目 | DeepSeek-Quyet | GLM-Quyet | 理由 |
|---|---|---|---|
| 書き手の L1 | DeepSeek-V4.1 DP6/EP6、nightly + SM120 パッチ、DSpark 5 | GLM-5.3-Flash TP2 × DP3 / EP6、標準 vLLM v0.31.0、MTP 3、NCCL、FP8 KV 16.75 GiB 固定、8K バッチ、0.95 | `glm-5.3-flash-6gpu` で計測して選んだ構成をそのまま使う |
| イメージ | DeepSeek 用パッチ版 + vLLM v0.31.0（Quyet）+ アダプター | GLM と Quyet で同じ標準 vLLM v0.31.0 ダイジェスト + アダプター | GLM にパッチは不要。`vllm-sm120.Dockerfile`、`patch_sm120.py`、`check_sm120_kernels.py` はコピーしない |
| プールの capabilities | `allow_chat_template_kwargs: [enable_thinking]` | なし | GLM は常に推論する。推論の強さは `reasoning_effort` で指定する |
| プールのチャット設定 | `legacy_chat_models` | `upstream_chat_models`（#647 が必要） | #647: 会話をまとめて送ると GLM がツールを呼ばなくなる |
| `default_reasoning_effort` | high（DeepSeek 公式） | **オーナー決定**、`max`（GLM 公式）を提案 | 「決めていただきたいこと」を参照 |
| サンプリング | temperature 1.0、top_p 0.95 | temperature 1.0、top_p 0.95 | GLM の `generation_config.json`。変更なし |
| F2 の判定文言 | 「JSON、DSML、またはコードブロック」 | 「JSON、`<arg_key>`/`<arg_value>` 表記、またはコードブロック」 | 本文に漏れるのは GLM 自身の呼び出し表記（`glm47` パーサー） |
| ワーカー名 | `deepseek`、プロファイル `deepseek_think` | `glm`、プロファイル `glm_think` | 名前だけ。`verification.py` のトレースのキーもこれに合わせる |
| WebUI のフィルター | 推論の強さ + DeepSeek 用の処理 | GLM 用のフィルター: `reasoning_effort` だけを送る | PR #644 での発見 |
| ストレージ | DeepSeek + Quyet | GLM 305.8 GiB + Quyet 62.5 GB + キャッシュ: `minimum_free_gib` 450 | |
| ポート | API 8013、UI 3012 | API 8016、UI 3017、L1 確認用 8017〜8021 | どの example も使っていない番号 |

`verified-tool.yaml` のそれ以外はそのままコピーする: 候補数 10〜16、候補ごとの
評価 6 つ（1 回の読み取りで 32 問まで）、answer と修正のプロンプト、形式チェックの
7 問（しきい値 0.5、strict モード）、修正は最大 2 回、Quyet の状態（ルート 12,000
文字、評価 8,000、形式チェック 6,000）、`prefer: TOOL >= 0.1`、判定のタイムアウト
60 秒と think ルートへのフォールバック、予算 `max_steps` 10 / `max_refine_depth` 2、
`expose_intermediate_outputs: false`、`answer` と think ルートの `max_tokens`
262,144、`internal_max_tokens` 131,072、書き手プールの `timeout_s` 7,200、
`server.max_concurrency` 128。これらについては、GLM にもこのハードウェアにも値を
変えなければならない理由がない。vLLM は 1,048,576 トークンのコンテキスト内で
262,144 トークンの出力を受け付ける。

## 決めていただきたいこと（オーナー）

1. **推論の強さの既定値。** GLM 公式の既定は `max`。DeepSeek-Quyet は `high`
   （DeepSeek 公式の既定）だった。PR #644 の計測では、`low` と `high` のとき GLM は
   ツールを使うターンで推論をすぐ閉じて答えた（13 トークン）。そのため `high` では
   候補と回答がエージェントのターンで推論しなくなるおそれがある。提案: `max`
   （公式を優先し、#647 の DeepSWE 実行でオーナーが選んだ強さとも同じ）。GPU 検証で
   TOOL ルートのレイテンシを記録し、c16 の serving 中央値がエージェント 1 ターンの
   上限 900 秒を超えたら、`high` に変える前にオーナーに再確認する。
2. **example の名前** `glm-5.3-flash-quyet-8gpu`（提案）。
3. **データセット。** `datasets/tool-routing-set.json` と
   `datasets/tool-turns.json` をそのままコピーする（提案）。ゲートの結果を
   DeepSeek-Quyet と 1 対 1 で比べられるようにするため。
4. **DeepSWE 実行。** ゲートが通った後に、この example で max の DeepSWE を回し、
   #647 の GLM 単体の実行と比べる（提案。GPU で約 1〜1.5 日）。

## テスト（CPU）

テスト方針どおり、受け付ける入力と外から見える結果を確かめる。静的な設定を
なぞるだけのテストは書かない。

- `test_gateway_builds_from_the_example_configs`: `kairyu.yaml` と
  `verified-tool.yaml` を読み込んでゲートウェイが組み立てられること（設定や DSL の
  ずれを防ぐ）。
- `test_compose_gpus_match_the_allocation`: GLM が 0〜5、Quyet が 6 と 7、TP ペアが
  `dp_rank_gpu_ids` どおりであること（GPU の指定を間違えると使用中の GPU で起動して
  しまう）。
- `test_think_is_one_glm_answer_at_the_callers_effort`（default/low/high/max で
  パラメータ化）: GLM への送信が 1 回で、`reasoning_effort` が呼び出し元の値
  （または既定値）と一致し、**`chat_template_kwargs` がない**こと（GLM 用の新しい
  約束: `enable_thinking` を付けると GLM のプロンプトが変わるか拒否される）。入力は
  複数ターンのエージェント会話（アシスタントのツール呼び出しとツール結果を含む）で、
  GLM への送信がそれらのターンを 1 つのユーザーメッセージにまとめず、ターンのまま
  運ぶこと（#647 の不具合を L2 の境界で確かめる）。
- `test_tool_route_judges_candidates_then_checks_the_replys_form`: 偽の GLM と
  偽の Quyet（33 問以上は拒否する）で、candidates → 6 × n の評価 → answer → 形式
  チェックの順に動き、公開される回答に構造化されたツール呼び出しが入り、推論の強さが
  candidates と answer に届くこと。
- `test_a_reply_failing_the_form_check_is_fixed_and_checked_again`: 修正して通る
  場合と、2 回修正しても通らず最後の回答が公開される場合。
- `test_a_reply_too_long_to_check_whole_is_published_unverified`: strict が拒否
  したとき `kairyu_verification.guaranteed` が false で、回答は公開されること。
- `test_an_unavailable_route_judge_routes_to_the_think_answer`。

L2 のテストは DeepSeek-Quyet のテストファイルと同じ形になる。各 example が自分の
設定のコピーを持つため。GLM 固有に加えるのは送信内容の確認（推論の強さ、テンプレート
kwargs なし、ターンのまま）だけ。`upstream_chat_models` の起動時チェックは、
ゲートウェイ組み立てのテスト（と #647 自身のテスト）で確かめられるので、別のテストは
作らない。プロンプトの文言、ポート番号、固定値のテストは追加しない。

ドラフトを外す前の確認: `uv run ruff check .`、`uv run pytest
tests/unit/test_glm53_quyet_example.py tests/unit/test_frontier_examplectl.py`、
その後 CPU の全テスト。

## GPU 検証（残タスク。8 × RTX PRO 6000 のホストが必要）

ゲートの前に、#647 の事前確認と同じやり方で次を行い、MEASUREMENTS に記録する
（約 15 分）:

- 複数ターンのエージェントのターンについて、`answer` と `glm_think_answer` の
  Kairyu から vLLM への送信内容をそれぞれ 1 つ取得する。呼び出し元のメッセージが
  ターンのまま（ツール呼び出しとツール結果を含む）で、`reasoning_effort: max` が
  入っていること。その送信内容を vLLM の `/tokenize` に通すと
  `Reasoning Effort: Max` が描画されること。
- #647 で止めた実行（`deepswe-glm-5.3-flash-6gpu-8w-20261012-r1`、5 メッセージ）の
  2 ターン目のリクエストを `kairyu-verified-tool` に 5 回送る。5 回とも TOOL ルートに
  なり、5 回とも構造化されたツール呼び出しが返ること（GLM 単体のプールは古い経路で
  1 回も返さなかった）。

続いて `datasets/tool-turns.json` の 6 ターンを TOOL ルートに流す: 候補数
（10 以上）、`glm47` 推論パーサーと MTP を使った状態での GLM の `response_format`
出力が JSON として正しいか、評価の読み取り時間と切り詰め、形式チェックの判定と修正、
複数呼び出しをまとめた回答。64 ターンのルート判定のやり直しは行わない。ルート判定は
会話しか読まないので、結果は DeepSeek-Quyet の実行と同じ（64 中 5）になる。

| # | ゲート | 合格条件 | 時間の目安 |
|---|---|---|---|
| 1 | `l1` | GLM の全 DP エンジン（正確な確認、low/high/max の推論の強さの描画、MTP でのプレフィックスキャッシュの一貫性、ツール呼び出し、画像）。エンジンごとの KV プールが 1,048,576 以上。各 Quyet レプリカの System One。strict の名前が切り詰めの必要な状態を拒否する。公開モデルから構造化された呼び出しが 1 つ返る | 15 分 |
| 2 | `routing` | 両半分で TOOL の見逃し 10 % 未満、THINK の適合率 90 % 以上 | 30 分 |
| 3 | `think-route` | 日常的なリクエストが既定の推論の強さで think ルートからストリームされる | 30 分 |

GPU で注意するリスク:

1. vLLM v0.31.0 で `glm47` 推論パーサーと MTP 3 を使った状態での、GLM の構造化
   JSON（`json_schema`、10〜16 項目）。JSON が不正だったり途中で切れたりすると
   candidates の役割が失敗する。
2. 推論の強さ `max` での candidates のレイテンシ（1 回の呼び出しで最大 131,072
   トークン）。
3. GLM のツール呼び出し表記が本文に漏れる（F2）割合が、DeepSeek の DSML より高い
   可能性。
4. `candidates` はエージェントの会話を JSON 文字列としてプロンプト内で読む（会話を
   そのまま渡す役割にはできない）。#647 で、GLM はまとめられた会話ではエージェントの
   手順を見失うと分かった。ゲート前の確認で候補数と正しさを測る。失敗した場合の
   修正は example 側（プロンプトや役割の構成）で行い、まずオーナーに相談する。
5. ホストメモリ: 1 台のホストで GLM の 6 GPU レプリカと Quyet 2 台を動かす
   （DeepSeek-Quyet では 256 GiB 以上の空きが必要だった）。
