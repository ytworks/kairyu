# GLM-5.3-Flash + Quyet example 計画

状態: 承認 2026-10-12（VCO-D23）。ブランチ: `claude/glm-5.3-flash-quyet-8gpu`。

## 1. 目的

`deepseek-v4.1-quyet-8gpu` の構成（Quyet によるルート判定と verified tool route）
で、書き手を DeepSeek-V4.1 から GLM-5.3-Flash に替えた example
`examples/glm-5.3-flash-quyet-8gpu` を新しく作る。DeepSeek 版はそのまま残す。

## 2. 前提

- PR #647 がマージされていること。GLM プールに使う `upstream_chat_models` 設定は
  #647 で追加されるため。
- `kairyu/` は変更しない（6 章）。

## 3. 構成

| 層 | 内容 | 出どころ |
|---|---|---|
| L1 書き手 | GLM-5.3-Flash、GPU 0〜5、TP2 × DP3 / EP6、MTP 3、標準 vLLM v0.31.0 | `glm-5.3-flash-6gpu` の構成をそのまま使う |
| L1 判定役 | Quyet-1.0-Large 2 台。GPU 6 はルート判定、GPU 7 は候補の評価と形式チェック | `deepseek-v4.1-quyet-8gpu` の構成をそのまま使う |
| L2 | `verified-tool.yaml`。書き手の役割（candidates、answer とその修正、think ルート）を GLM にする | `deepseek-v4.1-quyet-8gpu` |
| L3 | 公開モデル `kairyu-verified-tool`、Open WebUI | `deepseek-v4.1-quyet-8gpu` |

## 4. 元の example からの変更（GLM のために必要なものだけ）

| 項目 | 変更前（DeepSeek-Quyet） | 変更後 | 理由 |
|---|---|---|---|
| 書き手のモデルと L1 設定 | DeepSeek-V4.1 DP6/EP6 | GLM-5.3-Flash（3 章のとおり） | 書き手の置き換え |
| vLLM イメージ | DeepSeek 用の SM120 パッチ版 | 標準 vLLM v0.31.0（Quyet と同じイメージ） | GLM はパッチなしで動く（`glm-5.3-flash-6gpu` で確認済み） |
| プールの `allow_chat_template_kwargs` | `[enable_thinking]` | なし | GLM には `enable_thinking` がなく、推論の強さは `reasoning_effort` で指定するため |
| プールのチャット設定 | `legacy_chat_models` | `upstream_chat_models` | `glm-5.3-flash-6gpu` と同じ設定にするため（#647） |
| 推論の強さの既定値 | `high` | `max` | GLM 公式の既定（オーナー決定） |
| 形式チェック F2 の文言 | 「JSON、DSML、またはコードブロック」 | 「JSON、`<arg_key>`/`<arg_value>` 表記、またはコードブロック」 | 本文に漏れうるのは GLM 自身の呼び出し表記であるため |
| ワーカー名 | `deepseek`、`deepseek_think` | `glm`、`glm_think` | 書き手の置き換えに合わせた名前の変更 |
| WebUI のフィルター | DeepSeek 用 | GLM 用（`reasoning_effort` だけを送る） | `glm-5.3-flash-6gpu` と同じ。`chat_template_kwargs` を付けると 400 エラーになるため |
| ストレージの必要空き | DeepSeek + Quyet の分 | GLM 400 GiB + Quyet 80 GiB。取得前に 1 回、未取得の分だけを合計して確認（新規なら 480 GiB） | それぞれの元の example の値（`glm-5.3-flash-6gpu`、`quyet-1.0-large-1gpu`）。PR #648 レビューで修正 |
| ポート | API 8013、UI 3012 | API 8016、UI 3017、L1 確認用 8017〜8021 | 既存の example と重ならないようにするため |

## 5. 変更しないもの

ルート判定の質問・選択肢・TOOL の下限 0.1・タイムアウト 60 秒・think への
フォールバック、候補 10〜16、候補ごとの評価 6 問（1 回 32 問まで）、answer と修正の
プロンプト、形式チェック 7 問（しきい値 0.5、strict モード）、修正は最大 2 回、
Quyet の状態の上限（ルート 12,000 文字、評価 8,000、形式 6,000）、予算
`max_steps` 10 / `max_refine_depth` 2、`max_tokens` 262,144、
`internal_max_tokens` 131,072、プールの `timeout_s` 7,200、
`server.max_concurrency` 128、サンプリング（temperature 1.0、top_p 0.95）、
`expose_intermediate_outputs: false`。

## 6. フレームワーク（`kairyu/`）: 変更なし

- 推論の強さは `reasoning_effort` として送られる（`openai_backend.py`
  `_validated_request_payload`）。
- `enable_thinking` は、プールが許可しているときだけ付く（`conductor.py`
  `_worker_chat_template_kwargs`）。GLM プールは許可しないので、GLM には付かない。
- チェックリスト検証、strict な System One、会話をそのまま渡す publisher 役は、
  どれもモデルに依存しない（m1 D8、m1 D9）。

## 8. テスト（CPU）

`tests/unit/test_glm53_quyet_example.py` を新しく作り、`test_frontier_examplectl.py`
の一覧に追加する。

- 設定を読み込んでゲートウェイが組み立てられる。
- compose の GPU が割り当てと一致する（GLM が 0〜5、Quyet が 6 と 7）。
- think ルートは GLM への送信 1 回。推論の強さは呼び出し元の値（指定がなければ
  `max`）で、`chat_template_kwargs` はない。会話はターンのまま渡る。
- TOOL ルートが candidates → 評価 → answer → 形式チェックの順に動き、構造化された
  呼び出しが公開される。
- 形式チェックで落ちたら修正して再チェックし、2 回で打ち切って最後の回答を公開する。
- 長すぎてチェックできない回答は、検証なしで公開される。
- ルート判定が応答しないときは think ルートへ流れる。

lint（`uv run ruff check .`）、上のテスト、CPU の全テストを通す。
