# DeepSeek-V4.1 + Quyet: Quyet replaces Winnow, verified tool route rebuilt (2026-10-11)

Status: approved 2026-10-11 (VCO-D21, VCO-D22). Branch: `claude/deepseek-v4.1-quyet-8gpu`.

## Context

`examples/deepseek-v4.1-winnow-8gpu` (VCO-D18..D20) runs DeepSeek-V4.1 DP6/EP6 on
GPUs 0-5 and two Winnow-12B Q8_0 replicas used only through System One: GPU 6
judges the route (TOOL / THINK), GPU 7 judges the verified tool route's drafts.
Owner decisions 2026-10-11:

1. Quyet-1.0-Large replaces both Winnow replicas (VCO-D21), served as in
   `examples/quyet-1.0-large-1gpu`: stock vLLM v0.31.0 bf16 behind an
   example-owned System One adapter that keeps the `quyet` package's prompt and
   calibration. Quyet is used within its documented 6,000-token state.
2. The verified tool route (TOOL) is rebuilt (VCO-D22): no requirements;
   DeepSeek lists ten or more candidate tool calls for the next move from
   different viewpoints (one request); Quyet judges each candidate; DeepSeek
   writes the reply from the candidates and the judgments, batching several
   calls in one move when that is safe; Quyet checks the reply's form; a reply
   that fails is fixed by DeepSeek and checked again.
3. Routing (Quyet route judge, TOOL / THINK, fallback THINK, same question and
   choices) and the think route stay as they are.

The framework (`kairyu/`) is not changed. Nothing in it is Winnow-specific.

## Facts

- Quyet-1.0-Large: 62.5 GB bf16, one GPU on vLLM; System One only, text only,
  at most 10 options. The state is cut at 6,000 tokens (prompt at most 8,000):
  a dict keeps its beginning, a list its end. The adapter accepts 32 questions
  per request. About 2,400 prompt tokens per second per GPU.
- DeepSWE `deepswe-verified-tool-4w-20261009-r2` (975 turns): Winnow read a
  median 34,873 tokens for the route and 43,779 for the judgments; median
  conversation 158,907 characters (8 % fit 12,000); Quyet's tokenizer gives
  2.4-3.1 characters per token on these turns (Japanese 2.1). Of 966 replies,
  2 had no call, 1 wrote a call as text, 247 made two or more calls.
- Framework mechanisms used (no change):
  - a checklist verifier expands questions per item of a role's JSON list
    (`foreach`, flat item fields only) and splits them into parallel reads of
    the same state (`max_questions_per_call`);
  - a checklist verifying the final unit refines that same role with its
    `refine_prompt` (`{previous}`, `{feedback}`), up to `max_refinements`, and
    publishes the last attempt on exhaustion; unavailable System One publishes
    unverified;
  - the verifier sees the reply's calls as `<tool_call>{...}</tool_call>`
    envelopes after its text;
  - a final unit with a checklist is not streamed live.

## Verified tool route (L2, `verified-tool.yaml`, profile `primary`)

```text
TOOL
 ├ candidates    DeepSeek, caller's effort: 10-16 candidate tool calls C1..Cn for the next
 │               move from different viewpoints, one call each {id, viewpoint, purpose,
 │               name, arguments}; one request for all candidates
 ├ judgments     quyet-judge: 6 questions per candidate (60-96), read 32 at a time in
 │               parallel; informational (threshold 1.0 passes every p to the answer)
 ├ answer        DeepSeek, caller's effort, native conversation: reads the candidates and
 │               judgments critically and writes the reply; batches several calls in one
 │               move when each is sound, none depends on another's result, the
 │               conversation does not limit a reply to one call, and none is the
 │               finishing call (which goes alone, after success is shown); may fix a
 │               candidate, or write a sound call when no candidate is
 └ format_check  quyet-judge: 7 questions on the reply (threshold 0.5)
      PASS -> published
      FAIL -> answer re-sent with its refine_prompt (the previous reply and the
              failing items; change only what they require, keep the move) ->
              format_check again; at most 2 fixes, then the last reply is published
```

Candidate questions (noul; the candidate's name, arguments and purpose go in
the question):

| ID | True when | Source |
|---|---|---|
| now | the move needed now: advances the request and rests only on results the conversation shows | skipping ahead (VCO-D19/D20), calendar-first-move |
| new | repeats no step whose result the conversation shows | repeat-read, re-exploration |
| fits | fits the caller's tool name and parameters and the conversation's protocol | tool mismatch |
| exact | uses the request's names, paths, entry points and wording exactly and reads the request as written; a check it adds follows the request | public-name, own-check, wrong-column |
| check | a check uses the public path, build mode and static checks existing checks use, and "all" on more than one case (true when it checks nothing) | type-check, every-exporter |
| safe | destroys, overwrites or reverts nothing the request needs, changes nothing the request keeps, does not finish early | must-not-warn, partial-revert, finish-batched |

Form questions (noul, on the reply):

| ID | True when | Source |
|---|---|---|
| F1 | every action the text says it takes now is made as a call | announced-no-call (9 replies) |
| F2 | the text holds no call, command, arguments or call markup | calls as text (35/54, 3/47, 3/12) |
| F3 | every call names a declared tool with arguments valid for its parameters | schema |
| F4 | the reply makes at least one call | "No tool calls found" |
| F5 | batched calls do not depend on each other's results; one call when the conversation allows one per reply | batching (new) |
| F6 | a finishing call is alone and follows results showing every step it depends on succeeded (true without one) | finish-batched |
| F7 | the text is short and never mentions candidates, judgments or other internal material | stage leakage (VCO-D19) |

Quyet's states (inside 6,000 tokens):
- route judge: `max_conversation_chars` 120,000 -> 12,000 (fits Japanese);
- judgments: `conversation` (4,000 per message, 8,000 total), then `tools`;
  each candidate in its questions;
- format_check: `answer`, `tools`, then `conversation` (6,000 total), so a cut
  never removes the reply.

Budget: `max_steps` 6 -> 10, `max_refine_depth` 0 -> 2; `judgments` keeps
`max_refinements: 0`.

Owner-approved settings: at most 2 fixes, then the last reply is published;
form threshold 0.5 (VCO-D16: 0.99 sent near-passes to repair and broke moves);
at most 16 candidates; F5 and F6 are form questions.

Limits that follow from the framework (documented, not changed):
1. When the judgments cannot be read (Quyet down, or a candidate over about
   20,000 characters), the form check is skipped and the reply is published
   unverified (m1 D8: a run shares one unjudgeable flag).
2. The fix is the `answer` role again (same worker and effort); the previous
   reply reaches it as text.
3. A DeepSeek error during a fix fails the request.
4. The verified tool route is not streamed.

Estimated latency without fixes: candidates 40-80 s, judgments 10-20 s,
answer 30-60 s, form check 3-4 s; about 80-160 s (the previous route's p50
was 122 s, mostly the max-effort requirements, now removed). Each fix adds
about 30-60 s.

## GPU verification

Before the gates (recorded in MEASUREMENTS): 64 real DeepSWE turns that each
need a call, from `deepswe-verified-3wave-nextstep-4w-20261007-r1` (Winnow
routed 1 of 64 THINK), through the route judge one at a time: THINK count
(at most 6), truncated reads, read time. Six of them through the TOOL route:
candidate count (at least 10), judgment read time and truncation, form verdicts
and fixes, whether a fix changed the move beyond its failing items, batched
replies.

| # | Gate | Pass | Budget |
|---|---|---|---|
| 1 | `l1` | every DeepSeek DP rank; System One on each Quyet replica; one structured call from the public model | 10 min |
| 2 | `routing` | TOOL miss < 10 % on both halves; THINK precision >= 90 % | 30 min |
| 3 | `think-route` | everyday requests stream from the think route at the default effort | 30 min |
| 4 | `effort` | the caller's effort reaches the think route, candidates, answer and fixes; route judged on `quyet_route` | 90 min |
| 5 | `verified-tool-route` | 12/12 TOOL; >= 10 candidates; 6 x n judgments on `quyet_judge` (<= 32 per read); form check after the answer; structured call to a declared tool; fixes, publish reason and batched calls recorded | 120 min |
| 6 | `fallback` | route replica down: THINK with a call; judge replica down: TOOL, judgments unavailable, published unverified with a call; both back: judged and form-checked | 60 min |
| 7 | `serving` | c1/c4/c8/c16 (8/16/16/32) all answered, every reply a structured call; latency, tokens, tok/s per route | 40 min |
| 8 | `serving-routed` | routing set at the same levels, all answered; route mix and latency | 30 min |
| 9 | `browser` | Open WebUI answers | 5 min |

Every gate also records Quyet's truncated reads and read times, compared with
the Winnow run of 2026-10-09.
