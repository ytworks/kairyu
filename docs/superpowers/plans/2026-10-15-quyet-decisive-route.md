# 計画：main のマルチターンのルート（候補方式）はそのままにして、「まだ何も変更していない段階」だけそこへ送るようにルート判定を変える

状態: 承認 2026-10-15（VCO-D25）。ブランチ: `claude/quyet-decisive-route`（PR #653）。前の方針（PR #652、VCO-D24 の 1 回返答方式）はクローズした。この計画の前の版（「最初に本体を書く手」だけを送る案）は、Quyet がその手を見分けられなかったので取り下げた。

## 言葉（源流＝DeepSWE のハーネス mini-swe-agent のプロンプトから）

- **タスクメッセージ:** 最初の user メッセージ。課題文と決まった指示（手順①〜⑥、提出のコマンド、コマンドの決まり）からなる。
  - 手順：①関連ファイルを探して読む、②問題を再現するスクリプトを作る、③ソースを編集する、④スクリプトを再実行して確かめる、⑤端のケースをテストする、⑥ `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT` だけを出して提出する。
- **返答:** アシスタントのメッセージ。説明の文と、bash のツールコール 1 つ以上からなる。
- **ツールの結果:** `{"returncode", "output"}` の形のメッセージ。**エラー**は returncode が 0 でないこと。
- **変更:** ファイルを作る・書き換える・消す・移す、パッケージを入れる、コミットする、のどれかをするツールコール。読む・一覧を見る・探す・プログラムを動かして出力を見るのは、変更ではない。
- **単体のルート（SINGLE）:** 今の deepseek_think（GLM は glm_think）。書き手が会話をそのまま受け取り、1 回で答える。
- **マルチターンのルート（MULTI）:** main の verified tool（候補 → 判定 → 答え → 形式の確認）。DSL は変えない。
- どちらのルートも、エージェントが送った会話をそのまま受け取る。要約は使わない。

## ファクト

### Quyet がルートを決めるときに見えるもの（Kairyu のコードと、単体 max の実際の会話から）

- タスクメッセージは先頭 4,000 文字だけ見える。課題文が全部残るのは 78 %、手順①〜⑥が残るのは 93 %。
- 直前のツールの結果は 1 件見える。
- その手前は、返答 3 つとツールの結果 4 つほど（中央値）が見える。それより前は見えず、見えないメッセージは中央値で 200 件。Quyet にはその件数だけが渡る。

### 段階ごとの効率（マルチターン high と単体 max、1 問あたり）

| 段階 | 時間 | API コール数（L3） | 入力（L1） | 出力（L1） |
|---|---:|---:|---:|---:|
| まだ何も変更していない段階（主に手順①） | 0.93 倍 | 0.07 倍 | 0.39 倍 | 1.31 倍 |
| 最初の変更を書く 1 手 | 172 秒 対 23 秒 | — | — | 15.7k 対 1.7k |
| 変更した後のすべて（読む、実行する、変更する、エラーの後、提出） | 1.4〜10 倍 | — | — | — |

- 変更した後の読み取りは、単体だと短く（1 問に 26 回、1 回あたり平均 31 秒）回数が多い。マルチターンに回すと 1 回あたり約 200 秒になる。
- 時間の数字は、エージェントの記録の時刻差で測った（Kairyu 側の計測と、差の中央値 0.1 秒で一致）。

### Quyet が条件を読めるか（記録のターン 651 件で試験）

| 記録のターン | 正しいルート | MULTI に送った割合 |
|---|---|---:|
| まだ何も変更していないターン（マルチターンの会話、153 件） | MULTI | 98.7 % |
| 変更の後のターン（単体 max の会話、385 件） | SINGLE | 0.3 % |
| 最初の変更を書くターン（113 件） | — | 96.5 % |

- 「次の返答に変更が入るか」は、Quyet にも、DeepSeek の要約を足しても読めなかった。要約を足すと、変更の後のターンを誤って送る割合が 10.4 % に増えた。このため、この条件と要約は使わない。最初の変更も MULTI が書く。

### thinking の受け渡し

- Kairyu 経由では、前のターンの thinking がエージェントに返らない。それでも DeepSeek は遅くならなかった（出力は平均 1.30 倍・中央値 0.38 倍、時間は 0.51 倍）。
- GLM は、起動したときに同じように確かめる。

## ルートの条件（どのターンも必ず 1 つに入る）

1. 次の返答にツールコールが要らない → SINGLE
2. Quyet に見える返答の中に変更がある → SINGLE
3. 見えないメッセージが 20 件を超える → SINGLE
4. それ以外 → MULTI

- 書き方：Quyet の選択式の問いで、選択肢は SINGLE と MULTI の 2 つ。より確率の高いほうに送る。`prefer` は使わない。
- `max_message_chars` は 4,000、`max_conversation_chars` は 12,000 のまま。ファクトはこの値で測った。
- フレームワークは変えない。DSL で変えるのは `profile_judge` の question と choices だけ。

## 見込み（単体 max と比べて。マルチターンの数字は high で測ったもの）

- 時間：約 +8 %（まだ何も変更していない段階 −0.3 分、最初の変更 +2.5 分、変更の後を誤って送る分 +2 分。1 問 51.4 分に対して）。
- API コール数（L3）：約 −12 %。入力（L1）：約 −1.5 %。出力（L1）：約 +14 %。
- 正解：最初の変更をマルチターンが書く。片方だけが正解した問題を調べたところ、その場面での勝敗はマルチターンの 7 勝 5 敗だった。テストを重ねて直す場面（マルチターンは 0 勝 6 敗）は単体に残る。
- まだ分からないこと：max でのマルチターンの時間（high より遅くなるはず）と、GLM でのマルチターンの時間。

   - `verification.py`：

## 実装中に決めたこと（2026-10-15）

- ゲートの文言の確かめで、変更が失敗した会話と、bash 以外のツール（予定の作成など）の変更を、Quyet が変更と読めなかった。問いを「アシスタントがすでにしたツールコールを先に見る」形に直し、変更の例（ファイル、記録、予定、メッセージ）と「失敗した変更も含む」を書き足した。
- ツールが要らない会話の判断には、main で検証済みの THINK の文言をそのまま使った。
- 直した文言での結果:

  - DeepSWE の記録のターン：まだ何も変更していないターンの 95.4 % を MULTI に、変更の後のターンの 0.3 %（385 件中 1 件）を MULTI に送った。
